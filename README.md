# Web Audit Kit for Freelancers

A private, browser-only workspace for turning manually authored website findings into branded client reports. Built with React, TypeScript, and Vite. No backend, account, API key, subscription, or runtime network access.

## Start the application

Run the project launcher:

```bash
bash start.sh
```

On Linux and macOS, use Bash. On Windows, use WSL or Git Bash; a `.sh` file does not run in a plain Windows command prompt. Keep `start.sh` with the project folder. It finds its own folder, opens `dist/web-audit-kit.html` with the desktop browser, and works even when you launch it from another directory.

When the built app exists, the launcher does not need Node.js, npm, internet access, or a server. If the build is missing, the script checks Node/npm, installs project dependencies with `npm ci` if needed, and builds the app. A missing or unsupported Node installation produces instructions rather than changing system software. Dependency installation requires internet access. To force rebuilding after source edits, use `bash start.sh --build`.

1. Choose **Create a report**, **Explore the example**, or **Open a saved project** on the welcome screen. A recovered browser draft opens in Project without replacing its contents.
2. Follow Project, Branding, Findings, Action Plan, and Preview using **Back** and **Next**. You can switch sections at any time. Missing details do not block saving or printing a draft.
3. Choose **Save editable project** to download a backup with the text, branding, and images. Check your Downloads folder.
4. Choose **Export client PDF** to open browser printing. Select Save as PDF and follow the paper-size instructions below.
5. To continue later, open the HTML application and choose **Open a saved project** (or **Open project** in the editor). Select your `.audit.json` backup inside the app. Double-clicking that backup may open a text editor; a PDF cannot restore an editable project.

The guide explains app controls. You supply the findings; the app does not scan or test websites. Choose **Exit guide** to hide the instructions, or **Help → Restart guide** to return to the first step without changing your project. Guide state stays outside downloaded project files.

On smaller screens, use **Select a finding** to switch between findings. Use the **Report order** arrows to move the selected finding. Open **Priority guide** for definitions, or read the help beneath the priority field.

The built HTML stays inside `dist/` as the browser runtime. The root HTML launch pages and ZIP archives have been removed; no archive is generated by the build.

**Verification status:** the production build, model tests, HTML packaging checks, and simulated UI tests pass. Actual browser execution through `file://`, image processing, browser downloads, print dialogs, and PDF appearance could not be verified in this environment because the sandbox blocks browser socket operations. See [verification/RESULTS.md](verification/RESULTS.md). Do not treat simulated tests as browser certification.

## Save project versus Export PDF

| Control | Result | Purpose |
| --- | --- | --- |
| **Save project** | Downloads `Client-Name.audit.json` | Editable backup including details, logo, screenshots, finding order, action order, and paper size |
| **Open project** | Opens a downloaded JSON file | Restores the editable project after validation |
| **Export PDF** | Opens the browser print dialog | Creates the document you send to a client |

The download message confirms that a download was **initiated**, not that your browser finished writing it. Check your Downloads folder. Keep the JSON alongside your PDF: a PDF cannot be reopened as an editable project.

Invalid JSON, unsupported schema versions, invalid fields, and unreadable or mismatched images produce an error before the current project is replaced. Replacing unsaved work requires confirmation. Finding, screenshot, logo, and action removal controls explain their effects.

## Printing to PDF

Select **Preview**, then choose **A4** or **US Letter**. Click **Export PDF** and use these browser settings:

- Destination: **Save as PDF** (or the operating system's PDF destination).
- Paper: match **A4** or **US Letter** selected in the app.
- Orientation: **Portrait**.
- Scale: **100%**. If your browser applies automatic scaling, inspect its preview before saving.
- Margins: **Default** so the document's page margins apply.
- Headers and footers: **Off** to remove the local filename, file URL, browser date, and browser page headers.
- Background graphics: optional. Enable them for subtle badge fills; priority text remains visible without them.

Application controls are hidden in print. Long observations and recommendations can flow across pages. Images retain their aspect ratio and are constrained to the printable area. The report is continuous on screen; the browser's print preview shows final pagination. Print engines can differ. Inspect the actual PDF before sending it, particularly after adding long text or portrait screenshots.

Export is also available from other sections. It switches to Preview and waits for report images before opening printing. Canceling the print dialog does not change report content or mark the project as saved.

## Local recovery and privacy

A best-effort draft is written to `localStorage` after a short pause and when leaving the page. A valid draft is restored when the same browser and origin make it available. The interface shows recovery status and unsaved changes.

Browser storage is not a project backup. It may be unavailable under `file://`, in private mode, when storage is disabled, or when image-heavy projects exceed the browser's quota. Renaming/moving the HTML file or changing browsers can also separate drafts. Browser cleanup can delete them. **Download a project file to preserve your work.**

This version holds one active project and one local draft per available browser origin. On a shared computer, downloaded JSON files and browser drafts contain client information. Use your browser's site-data controls to clear drafts when appropriate.

There are no analytics, remote fonts, CDN assets, network requests, or server uploads. Uploaded images are embedded in JSON and rendered from local data URLs. Imported text is rendered as text through React; HTML is not executed. Imported image data accepts only raster PNG, JPEG, and WebP, not SVG or remote URLs.

## Images and limits

- Input types: **PNG, JPEG, WebP**; static images only.
- Maximum original upload: **10 MiB** per image; maximum decoded input: **40 megapixels**.
- Screenshots resize to at most **2048 px** on the longest edge; logos resize to **800 px**. Smaller images are not enlarged.
- Images are re-encoded locally. Screenshots normally use WebP; logos start as PNG to preserve transparency. Oversized encoded images use a lower WebP quality or receive a clear error.
- Stored image data is limited to approximately **2.1 MiB** per image, depending on base64 expansion. Imported images allow up to 3 MiB of data URL text and must decode to their declared dimensions.
- Up to **8 screenshots per finding**, **50 screenshots per project**, **100 findings per project**.
- Project JSON maximum: **25 MiB**, including images. Text fields have input limits: 500 characters for short fields, 2,000 for contact details, 1,000 for captions, and 12,000 for long-form fields.

The interface uses the familiar label “MB” for these binary limits. Resizing and compression trade some image detail for manageable project files. Keep original evidence separately when full image detail matters.

## Typography and local fonts

The editor uses **Sora** for form fields and controls, with **Instrument Serif** for page headings and report titles. The layout uses warm paper colors, thin section rules, and a light navigation rail. Form labels remain 13 px and help text remains 12 px; inputs use 16 px text.

Both WOFF2 font files live in `src/assets/fonts/`. Sora uses one variable font file for its weights. Vite embeds both fonts as data URLs in the production HTML, so the app needs no font CDN or runtime network connection. The packer includes the copyright notices and complete SIL Open Font License in an inert `font-licenses` template inside the HTML; the source includes separate license files.

Font credits: [Sora](https://github.com/sora-xor/sora-font) and [Instrument Serif](https://github.com/Instrument/instrument-serif). See the bundled [Sora license](src/assets/fonts/Sora-OFL.txt) and [Instrument Serif license](src/assets/fonts/Instrument-Serif-OFL.txt).

Font changes can alter line wrapping and PDF pagination. Review exported PDFs before sending them; actual browser font loading and PDF appearance remain unverified in this sandbox.

## Development

Prerequisite: **Node.js 22.22.2+ within Node 22 LTS** (or Node 24.15+ / 26+) and npm. Dependencies are needed only for development and building. The packaged HTML needs neither Node.js nor an internet connection.

```bash
npm ci
npm run dev
```

Open the local URL Vite prints, normally `http://localhost:5173`. All application data still stays in the browser. Development and production/file origins have separate local drafts.

```bash
npm run build
npm test
```

`npm run build` type-checks TypeScript, runs Vite, then inlines the generated JavaScript and CSS with `scripts/pack.mjs`. It removes separate generated asset files. The resulting files are identical standalone applications:

- `dist/web-audit-kit.html`: identical portable application in the build directory.
- `dist/index.html`: same application, convenient for static hosting or `npm run preview`.

The build intentionally uses one JavaScript bundle. Vite may warn that it exceeds the default 500 kB chunk threshold; splitting it would conflict with the single-file deliverable. Assets and example images are embedded locally. The packer fails if an external script or stylesheet reference remains.

`npm test` runs data validation/report rendering tests and UI workflow tests against the **latest production build**. Run the build first after changing source. UI tests use jsdom and simulated download/print APIs; they do not validate real image decoders, the file download system, browser printing, layout, or file-origin storage policy.

Documentation references: [React createRoot](https://react.dev/reference/react-dom/client/createRoot), [Vite production builds](https://vite.dev/guide/build).

### Real browser verification

`tests/browser_workflow.py` is the browser acceptance harness. It requires Python 3, Pillow, Playwright, and Playwright browser binaries in a machine that permits browser processes. These tools are optional and are not runtime/build dependencies.

```bash
python3 -m pip install playwright pillow
python3 -m playwright install chromium
python3 tests/browser_workflow.py
```

Set `AUDIT_CHROMIUM_EXECUTABLE` if you need a specific Chromium executable. By default the script uses Playwright's installed Chromium. The harness opens the packaged file with networking disabled, exercises uploads, editing, project downloads and imports, and generates A4/Letter PDFs for 0/1/20 findings plus long text and portrait-image cases under `verification/`. It verifies print invocation separately; a human still needs to inspect the browser print dialog and the resulting PDFs. For PDF text/page checks, install Poppler (`pdfinfo`, `pdftotext`, `pdftoppm`) separately if desired.

Repeat the manual matrix in [verification/RESULTS.md](verification/RESULTS.md) in the desktop browsers you intend to support. Firefox and Safari require manual print-to-PDF checks; Playwright's PDF API is Chromium-specific.

## Launcher and build output

`npm run build` updates the self-contained HTML files in `dist/`. `start.sh` opens that output; it does not host a backend or keep a server running. If a browser cannot open, the script prints the file path for manual opening. Developer rebuilds use the existing Node requirements above.

## Example project

Open `examples/brightside-cleaning.audit.json` with **Open project**, or use **Open example project** in the app footer. The same example is embedded in the HTML, so it is available offline.

Brightside Cleaning, Studio North, all observations, `.example` URLs/contact details, and screenshots are fictional demonstration content. Five editable findings cover the five supported categories. No live website was audited. No performance, revenue, search ranking, or website health measurements are claimed. Original illustrative mockups were generated locally with Pillow, not downloaded from another business. The report and each image clearly label the demonstration.

To regenerate the example and original mockups, optionally install Pillow and run `python3 scripts/make_example.py`, then rebuild. The generator uses locally installed DejaVu Sans; it is not needed to run or build the existing application. Change the font paths in that script if regenerating on another OS.

## Project format and source map

Project files use `schemaVersion: 1`. Every finding and image has an ID; `actionPlan` stores finding IDs in selected order. Older/newer unsupported versions are rejected rather than guessed or partially imported. Unknown properties are discarded after validating required fields. There is no automatic schema migration yet.

- `src/App.tsx`: editor, project file workflow, local recovery, print handoff.
- `src/model.ts`: schema, validation, limits, finding and action operations.
- `src/images.ts`: local resizing, encoding, and import image checks.
- `src/Report.tsx`: shared report preview/print document and cover preview.
- `src/styles.css`: interface, responsive layouts, dedicated print styles.
- `examples/`: editable fictional audit with embedded original mockups.
- `scripts/pack.mjs`: single-HTML packaging.
- `tests/`: model/report tests, simulated UI tests, and browser acceptance harness.

## Scope and limitations

This is a manual report authoring tool. It does not crawl websites, test accessibility automatically, generate recommendations with AI, assign numerical health scores, estimate lost revenue, or offer accounts, payments, cloud storage, or collaboration.

Effort labels are relative: Small, Medium, Large, or Unknown. Priority combines text and color: High means address a significant barrier first; Medium means schedule friction that has a workaround; Low means refine when practical. Auditors choose action ordering explicitly.

No desktop browser is certified by this build environment. File-origin storage and download/print behavior vary across browsers and operating systems. Real A4/Letter PDF appearance, keyboard focus behavior, and responsive layout require the pending browser checks documented in the verification results.
